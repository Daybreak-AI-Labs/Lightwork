## Executive result

Lightwork does **not** yet have every capability publicly marketed for the six
OneTrust offerings in scope. The strongest overlap is AI Governance and the
local privacy/security control planes. This working tree now also has coherent,
focused-test-covered local paths for a tenant-private six-suite governance
inventory, public web consent capture, versioned consent publishing, bounded
analytics, durable downstream delivery, scheduled tracker and native-
application scanning, device-bound native consent source contracts, governed
consent experiments, identity-bound OTT/CTV rights intake, Data Use Governance
policy compilation and native Snowflake and Databricks enforcement/audit
adapters, six named privacy-discovery readers plus a digest-only reviewed data-
map target, licensed-source regulatory research, third-party intelligence/due-
diligence controls, evergreen public/private policy links, five packaged
governance agents, multimodal AI Evidence Analysis, named cloud-agent governance
contracts, assessment-question comments, and a California DROP request/status
control plane. None of those local paths is proof of live provider
interoperability, customer-scale operation, regulatory acceptance, or literal
OneTrust parity. The largest remaining product gaps are compiled, packaged and
operated mobile/OTT consent host integrations, accepted branded/native cross-
channel trust centers, named MarTech/AdTech integrations, broad discovery
format/source/semantic coverage and live estate operation, live intelligence
feeds, end-to-end DSR automation, a hosted full-product customer sandbox/tenant-
copy service, and curated compliance-content and continuous-evidence breadth.
The refreshed public catalog also names packaged privacy/third-party agents,
multimodal AI evidence analysis, provider-specific Bedrock/Azure/Vertex agent
detection and a Databricks AI Security Framework outcome. Lightwork now has
coherent local product paths for those outcomes, but provider writes, durable
production cloud authority, licensed content, off-host token custody and live
customer/provider acceptance remain materially incomplete.

This is a public-claims inventory and an implementation map, not a source-code
comparison. OneTrust is not open source, its marketing claims were not tested
here, and contract-specific or customer-only features may not be visible on its
public site. The 149 rows normalize public product outcomes and sometimes group
multiple UI-level features; they are not proof that every toggle, workflow
variant, API, integration contract, or customer-only module was enumerated.
Conversely, a Lightwork module is not counted as parity merely because it has a
similar name: it must implement the same product outcome.

One especially important market-state distinction: OneTrust's public Data Use
Governance page currently presents a **Request Early Access** action. Every
Data Use Governance capability below is therefore a marketed early-access
claim, not a claim that this review independently established general
availability.

## Status definitions

- **Implemented**: a coherent Lightwork product path exists in this checkout,
  is mounted in the shipped product surface, has a shipped and documented
  production composition whose readiness can pass without test-only injection,
  and has focused automated coverage. This remains local repository
  implementation, not live-provider, customer-scale or third-party acceptance.
- **Partial**: useful code exists, but a material part of the advertised product
  outcome, mount, production composition/readiness, integration, breadth,
  deployment, or validation is absent. An isolated core plus a mounted API that
  deliberately reports unconfigured is Partial when the advertised outcome is
  a usable product or an out-of-box capability.
- **Missing**: no coherent implementation of the advertised outcome was found.
  Adjacent utilities, prompts, domain packs, or proposal documents do not count.
- **External / unverifiable**: the outcome depends on live providers, licensed
  content, commercial data, customer estates, independent acceptance, or
  operational scale that this repository cannot prove.

The row text uses five evidence stages so code and operating proof are not
collapsed into one label:

1. **Core** — domain logic and focused automated coverage exist.
2. **Mounted** — the shipped application exposes the API, page, scheduler or
   worker path.
3. **Configured / ready** — production configuration supplies every required
   authority, store, key, adapter and retention policy, and the shipped readiness
   check succeeds without fixtures or test-only `app.state` injection.
4. **Live interoperable** — the exact provider contract has passed against a
   consenting named test tenant or relying system.
5. **Operated / accepted** — recovery, concurrency, scale, privacy/security,
   usability and audit/export exercises have passed with the relevant customer,
   provider, legal, regulator or other relying party.

Stages four and five often require external evidence. They are never inferred
from local transport, mock or unit tests. Missing an external stage does not by
itself make every locally owned capability Partial, but missing a stage that is
part of the advertised outcome — such as "out of the box," continuous operation
or a named live integration — does.

## What must be true before claiming complete parity

A defensible statement that Lightwork has every capability above requires more
than adding matching class names. At minimum, the following evidence is still
required. Each row's acceptance record must identify the exact commit and
configuration revision; show core, mounted and configured/ready evidence
