# AI Evidence-Ready Gateway

The AI Evidence-Ready Gateway is Lightwork's deterministic delivery and
assurance boundary for text generated by an AI system. It adds required
disclosures, records a signed hash-only receipt, binds that receipt to the
active policy, model, and context digests, and exposes the evidence through the
existing `/security/assurance` cockpit.

It is evidence infrastructure, not a certification product or legal
determination. Regulatory applicability, policy approval, exceptions, control
mapping, and regulatory-impact disposition remain human-owned.

## Enable it

The capability is off by default:

```toml
[evidence_graph]
enable = true

[model_risk_assurance]
enable = true
gate_promotions = true

[evidence_gateway]
enable = true
```

Selecting the gateway in `maverick init` also enables the evidence graph and
Model Risk Officer so the combined assurance cockpit is complete. The gateway's
runtime gate remains independent: a hand-edited configuration may enable only
`[evidence_gateway]`; enable the two companion controls when their evidence and
promotion-governance features are wanted.

The runtime also requires an explicit tenant binding (`MAVERICK_TENANT` or an
authenticated client/tenant context). It refuses the legacy unbound namespace
instead of allowing evidence from different customers to share a store.

## What the gateway records

For each delivered text interaction, the gateway:

1. treats the payload as AI-generated content and refuses a caller attempt to
   disable that classification;
2. applies the approved disclosure fail-safe until a human-facing turn has
   consumed it, plus the configured machine-readable and visible markings;
3. binds the event to policy revision, model digest, context digest, modality,
   conversation hash, and input/output hashes;
4. emits an idempotent signed receipt; and
5. reports the receipt as `current` or `stale` against the active policy and
   bindings.

The durable receipt does **not** contain the raw input text or delivered output
text. Raw text exists only at the synchronous delivery boundary. Callers should
still apply their own retention, privacy, and content controls to the returned
text.

The policy metadata field is a closed governance allowlist (asset/owner IDs,
environment, jurisdiction, version, tags, and demo booleans), not a free-text
store. Visible-marker exceptions are not implemented in v1: both the core and
operator API refuse caller-supplied exceptions so a caller cannot self-assert
authority to suppress a marker.

Hash-only receipts reduce retained content; they are not a confidentiality
mechanism. Digests of low-entropy or repeated text can reveal equality and can
be guessed by an actor who already has candidate text. Protect the receipt
store and signing keys accordingly.

## Regulatory impact loop

An administrator can record a cited regulatory alert against affected gateway
policies, AI assets, and GRC control identifiers. Every citation must use HTTPS
and carry the retrieved content's SHA-256 digest. A separate administrator
accepts or dismisses the impact with a rationale and the expected record
revision. Accepting an impact updates the affected policy bindings; dismissing
one preserves the review history without changing policy.

The gateway does not infer affected controls from a title or an uncited
summary. Integrations should pass the explicit mappings produced or reviewed by
the regulatory-change workflow.

## Operator API

The API is nested under the existing Model Risk assurance prefix:

`/api/v1/security/assurance/gateway`

Operators with `operate` permission can deliver text, view policies and
receipts, verify receipts using server-owned trust anchors, and inspect
regulatory impacts. Policy mutation, regulatory-impact record/review, packet
issuance, and the demo seed require global `admin`. Delivery and packet
issuance are rate-limited.

Request schemas reject unknown fields and caller-supplied trust roots.

Packet issuance is an explicit `POST`, because it appends a signed attestation
to the packet ledger; a read-only `GET` does not issue evidence. The response
returns
`Content-Disposition: attachment; filename="lightwork-ai-assurance-packet.json"`
and `Cache-Control: no-store`. Offline verifiers should use a separately
provisioned trusted public-key registry; never trust a key merely because it is
included beside a packet.

Packets contain gateway policy, receipt, and cited-impact evidence only; they
do not silently claim to be the complete Model Risk or GRC evidence set. A
bounded evidence-window manifest records total/included/omitted counts and
ordered collection digests. Any omitted records make readiness false. Packet
generation rechecks the source collections before signing and asks the caller
to retry if they changed mid-export.

## Synthetic demo

The cockpit's **Load synthetic no-network demo** action creates only local,
synthetic gateway records. It is labeled `DEMO DATA`, is admin-only, performs no
feed fetch or model call, and does not alter the public `/demo` route. Seeding
is refused when the active tenant already contains non-demo gateway evidence;
use an empty, dedicated demo tenant. Demo evidence also forces the readiness
gap `synthetic_demo_data_present`.

## Benchmark evidence

The cockpit links the
[governance benchmark report](../benchmarks/GOVERNANCE_FRONTIER_RESULTS.md) and the
dashboard's `/benchmarks` history view. Treat benchmark results as scoped test
evidence: they establish only the controls, fixtures, versions, and runs named
in the report. They do not establish regulatory compliance or comparative
model quality outside that scope.
