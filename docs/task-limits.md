# Task limits and spend accounting

Ordinary goals no longer receive generated dollar, elapsed-time, token, tool-call
or 25-step limits. Omitted limits remain unset across the CLI, dashboard, MCP,
framework adapters, templates and imported workflows. Usage is still metered;
unset limits do not make provider usage free. Explicit evaluation and experiment
limits remain bounded independently of ordinary customer tasks.

## Existing installations

An existing numeric limit is preserved because Lightwork cannot tell whether it
was generated by an older installer or deliberately chosen by an operator.
Settings provides a reversible task-limits choice. Disabling it suppresses
configured, learned and saved deployment task defaults. The equivalent config is:

```toml
[budget]
task_limits_enabled = false
strict_pricing = true
```

Re-enabling the setting restores the saved defaults. An explicit invocation
limit, including `MAVERICK_BUDGET_DOLLARS` or `--max-dollars`, still applies.
Malformed explicit settings produce an error instead of silently removing a cap.
The installer offers no task limit by default and accepts an explicit dollar
choice. Configure a task cap by enabling task limits and setting, for example,
`[budget] max_dollars = 25.0`.

Organization allowances, role permissions, tool risk ceilings, consent, HALT,
cancellation, recursion/concurrency controls and repeated-failure safeguards
remain effective when task defaults are disabled.

## Organization allowance and uncertain provider charges

Organization admission checks the current allowance before each physical provider
attempt. Starting a task does not reserve its entire organization allowance.
Concurrent requests retain durable projected holds; known usage is reconciled
against a cumulative accounting receipt, without charging the same goal again
for each provider call. A provider retry is a separate physical attempt.

An interrupted request with an unknown charge retains its hold until the provider
receipt resolves it. It does not become free after a timeout. Organization
allowance refusals direct the customer to an administrator or unresolved-charge
review; removing a task limit cannot override that refusal. Released receipts
move to indexed history so completed work does not fill the pending-hold file.
Pending unresolved scopes remain subject to the 16 MiB store bound.

## Workflow progress and retry

Built-in workflow agents meter actual cost and return their business result text.
A known refusal before dispatch becomes `budget_limited`, retains the unfinished
invocation and does not publish a success result or train on a business failure.
An authorized retry with a larger finite total allowance continues saved work.
Nested invocation frames preserve completed iterations, branch outputs and the
captured subflow definition. HALT and allowance signals escape business-error
catch blocks.

An unknown external-effect outcome remains held for reconciliation. Ordinary
Agent checkpoints retain the existing opt-in `[durable] enabled` or
`MAVERICK_DURABLE` setting; durable workflow frames do not turn ordinary Agent
checkpointing on. Legacy embedded two-value executors without metered usage keep
their explicit `agent_budget_dollars` reservation contract, whose compatibility
default is $5. Production metered agents do not use that fallback.
